# Telegram Ads в рабочем проекте и Агентстве

Этот раздел нужен только при сохранении файлов в проекте или работе через установленный BB-плагин «Агентство». Job — задача плагина; ProjectBinding — её привязка к проекту и машине; ArtifactVersion — зарегистрированная версия результата; ProcessVersion — версия процесса отдела. Эти объекты берутся из установленного сервиса, не входят в пакет и не нужны для самостоятельного рекламного плана. Sidecar — отдельный файл метаданных рядом с файлом, чью схему менять нельзя.

## Контекст и границы

1. Для Job Агентства прочитай доступные Job/ProjectBinding, процесс отдела и назначенную версию сотрудника. Реальные departmentId, assignedAgentId, policy и reviewPolicy берутся оттуда. Рекламная специализация не создаёт отдел автоматически. При настройке сотрудника предложи telegram-ads в его skillIds через доступный интерфейс; чтение навыка не является назначением в базе.
2. Используй host и canonicalRoot из привязки проекта. Если плагина нет — подтверждённый пользователем рабочий проект. Сначала проверь существующие рекламные папки и ссылки знаний; принятые пути важнее предложенной структуры ниже.
3. Найди ссылки на продукт/оффер, аудиторию, голос бренда, дизайн-систему, посадочную и измерение результата в контексте проекта. Не копируй их в кампанию. Нет PROJECT.md — используй свободный бриф; нет root — верни содержательный результат в чате, не создавай папки в случайном проекте. Неизвестные существенные бюджет/валюту/цель не подставляй предположением для запуска.
4. Для плагинных операций используй документированные команды установленного «Агентства»; дополнительный навык agency необязателен. Файл на диске ещё не ArtifactVersion, approved в YAML не завершает Job. Нет интерфейса регистрации — сообщи «файл подготовлен, регистрация не выполнена». Не пиши напрямую в базу и не выдумывай команды запуска.

## Размещение результатов

Если принятой схемы нет, используй `<project-root>/marketing/telegram-ads/campaigns/<campaign-id>/`. Выбери стабильный slug кампании; это локальный ID, не ID кабинета или Job. Создавай только материалы запрошенного этапа, не пустое дерево полного запуска.

| Результат | Путь внутри кампании | Что сохранять |
|---|---|---|
| Бриф и готовность | BRIEF.md | Цель, ограничения, ссылки знаний, пробелы и проверка посадочной |
| Происхождение | sources.json | source_id, сервис/экспорт, время сбора, период, валюта, timezone, окно атрибуции, ограничения; неизвестное null |
| Оригинальные выгрузки | raw/<source>/<export-id>/ | Неизменённые файлы; секреты не включать |
| Подбор каналов | data/channels.json или .csv | [Таблица каналов](../assets/templates.md), source_id для наблюдений; причина include/reserve/reject |
| Нормализованная статистика | data/performance.json или .csv | Исходные ID, единицы, период, источник, правила преобразования |
| Анализ | analysis/<topic>.md | Выводы, гипотезы и проверяемые основания отдельно |
| План, тексты, тесты, исключения | deliverables/v<revision>/ | Нужные части [шаблонов](../assets/templates.md); ссылки между test_id, creative_id, channel/pool и tracking_id |
| Ревью и передача | checks/review-v<revision>.md, handoff.md | Проверенная версия, критерии, дефекты, владелец следующего действия |

Если Job уже задаёт папку результата, сохраняй там; не заводи параллельную копию ради этой таблицы. Один небольшой медиаплан может быть одним MD с разделами. Новый `work/tasks/…/task.json` для Job не создавай автоматически: плагин уже хранит задачу. Если файловый контракт проекта требует task-пакет, в нём ссылки на канонические результаты, а не копии.

Для MD применяй YAML стандарта agency-artifacts, когда навык доступен. В JSON добавляй метаданные только если схема разрешает; для raw/закрытых схем — sidecar. Не придумывай собственный несовместимый стандарт при отсутствии помощника. Department в документе согласуй с проектом; он не заменяет departmentId. Для Job общий task_ref — external + реальный Job.id. Версия документа и версия, выданная сервисом артефактов, учитываются раздельно.

## Происхождение и связи

Показы/клики/расход кабинета, подписки или start бота, события аналитики и продажи CRM сохраняй раздельно с их источниками. Соединяй только по подтверждённым ID/правилам атрибуции; не объявляй рост подписчиков конверсией конкретного объявления без основания. Метрики каталогов каналов не являются результатами рекламного теста. Преобразования raw → data фиксируй в анализе или журнале: поля, правило, затронутые строки.

## Передача между сотрудниками

- Рекламный специалист отвечает за гипотезы, таргетинг, бюджет и измерения; конкретный исполнитель определяется Job.
- Если требуется новый текст или визуал, передай соответствующему сотруднику цель, обещание, аудиторию, ограничения подтверждённого формата, ссылки на знания и test/creative IDs. Не создавай изображения по умолчанию для текстового объявления.
- Используй существующий механизм подзадач/передачи Агентства. parentJobId — иерархия; зависимость оформляется отдельно доступной операцией. Без интерфейса подготовь бриф передачи, не утверждай, что дизайнер назначен.
- Для файлового дизайн-брифа используй принятую design/requests/<request-id>/BRIEF.md либо ссылку из Job. Кампания ссылается на канонический бриф и версию ассета; не дублирует бренд или дизайн-систему.

## Проверка и следующий шаг

Маршрут полного запуска: бриф/готовность → каналы и гипотезы → план тестов/креативы/измерения → проверка процесса отдела → разрешённый запуск → наблюдение → решение об оптимизации. Узкая задача выполняет только относящиеся к ней этапы.

Ревьюер и участие человека определяются ProcessVersion.reviewPolicy и поручением, а не жёстко назначаются этим навыком. Проверь бюджет, происхождение чисел, связи тестов и объявлений, готовность измерений. Для внешнего запуска необходимы действующие разрешение и бюджетные границы; уже данное разрешение повторно не запрашивай. Принятие документа не разрешает расход автоматически.

Изменился оффер/бюджет/посадочная — проверь затронутые тесты, создай новую версию изменённого результата и передай её на требуемую проверку. Предыдущее принятие не переносится на изменённую версию. Оптимизация ограничена окном и бюджетом; укажи next_check_at или условие следующей проверки, не запускай бесконечный цикл. Исполнение сотрудника возможно только при доступном runtime, независимо от готовности плана.
